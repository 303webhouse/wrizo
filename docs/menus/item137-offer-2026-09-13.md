## §2 · S0 — THE HYPOTHESIS WAS MEASURED, NOT TRUSTED

| viewport | gap (aside.bottom − trash.bottom) | `.wz-strip` height | aside height |
|---|---|---|---|
| 1366×**768** | 8.8px | **544.4px** | 545.2px |
| 1366×**1200** | **303.6px** | **544.4px** | 840.0px |

**The gap grows 8.8 → 303.6.** That comparison was the instrument's verdict by
design: a content-tall strip's gap grows because the aside stretches while the
content does not; a genuinely pinned foot holds near zero at both.

**The explanation was measured beside the symptom and is decisive alone:**
`.wz-strip` rendered **the identical 544.4px at both heights** while the aside
tracked `70vh` exactly (0.70 × 1200 = 840). `height:100%` resolves against the
parent's **height**, and `min-height` does not make that definite — so the
percentage fell back to `auto`, the strip went content-tall, and
`.wz-strip-foot{margin-top:auto}` had no free space to consume.

**WHY THE FOUNDER SAID "INLINE" RATHER THAN "STRANDED".** At 768 the gap is
8.8px — the eye sees Trash sitting after the last item. **The defect was never
that Trash was slightly high; it was that Trash was never pinned at all**, and
it strands further the taller the window gets.

## §3 · THE FIX — GEOMETRY ONLY

`.desk-frame-strip` becomes a flex column; `.wz-strip` takes `flex:1` in place
of `height:100%`.

Stretching into a flex parent needs **no definite height on that parent at
all**, which is why this is the geometry fix rather than inventing a height
for the aside — inventing one would have put a second source of truth beside
`min-height:70vh` for the next lane to desynchronise.

| viewport | gap before → after | strip height before → after |
|---|---|---|
| 768 | 8.8 → **8.8px** | 544.4 → 544.4px |
| 1200 | **303.6 → 8.8px** | 544.4 → **839.2px** |

The strip now tracks its parent (839.2 against an 840.0 aside). The residual
**8.8px is structural** — `.wz-strip`'s 8px bottom padding plus the 1px border
— and is identical at both heights, which is what a pin looks like.

**`item137.mjs`: 9/9 green, and it bites 3/9 pre-fix** (baseline built the
lawful way — pre-fix CSS under the CURRENT harness):

| S1 @ 1200 — gap ≤ 14px | **303.6px** |

| S1 discriminating — gap stable across heights | drift **294.6px** |

**The load-bearing detail: S1 @ 768 PASSED on the broken build, at 9.0px.** A
check that only bounded the gap would have certified the bug as fixed. What
separates *pinned* from *accidentally close* is behaviour across heights, so
the discriminating assertion is that **the gap does not care how tall the
window is**. S2 asserts the mechanism itself, so a future change that restores
the bug is **named** by the check rather than merely detected by it.

**Nothing is parked.** No prior assertion covered the Trash's vertical
position — which is exactly why a founder had to report it — so the repair
falsifies nothing. The empty list is the evidence, not an omission.
