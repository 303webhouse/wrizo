## §2 · E1 — THE CAUSE WAS NOT WHERE THE OFFER RECORDED IT

**The offer's §7 named a permissive `band <= 0` return on a full-bleed canvas.
That was wrong, and it is corrected here rather than quietly dropped.**
Measured, the board's band is **+50px at 1366** and **+207px at 1680**. It is
never `<= 0`, so that branch never ran. The claim was a *reading* of the code
presented with the confidence of a measurement.

> **READING CODE IS A HYPOTHESIS. RUNNING IT IS A MEASUREMENT.**
> This lane's own law — "maps are research, disk wins" — applied to its own
> diagnosis. A located cause that was never executed is not a located cause.

### The actual mechanism

A diagnostic hook read the store while the sliver stood visibly
`data-open="true"`:

```
{ openDrawer: null, coexist: false }
```

**The policy was correct the whole time and was never consulted.** `coexist:
false` is the right answer; `openDrawer: null` is the bug. The store did not
believe any drawer was open, so `requestOpen('cascade')` found nothing to
displace and displaced nothing.

`Sliver.tsx` announced its opens from inside a `setState` updater, and **only
on the paths that ran through `toggleOpen`** — the Ctrl+/ shortcut. The grip's
own `onClick` called `setOpen(o => !o)` directly. The grip is the affordance a
writer **taps on a tablet**, which is exactly where Nick felt it.

**The law was never wrong. It was never told.**

### The repair is at the invariant, not on the silent path

Patching the grip's `onClick` would have fixed this bug and left its class
alive. Both drawers now announce from an **effect keyed on their own open
state**, so every path announces — grip, shortcut, dock, Escape, the exclusion
handoff, and any path written later. **A silent open path is no longer
possible to write.**

This also repairs an impurity that was wrong independently of E1: a `setState`
updater must be pure, and announcing from inside one meant closing the *other*
drawer — i.e. calling its `setState` — from within this component's render
phase.

### Two more of the same family, found only by measuring

- **The two-drawer law was DISABLED OUTRIGHT on screenplay.** `canCoexist`
  looked for the paper with `.mode-page, .board-canvas, .script-page`, and
  `.script-page` does not render on the framed screenplay surface. The
  diagnostic read `band=null` at both reference widths while `.script-sheet`
  read a real band of 191/348px. `querySelector` returned null, the function
  took its `!paper` early return, and the law simply never ran there. The
  selector list is now single-sourced with the probe's corrected one.
  `.board-canvas` → `.board-canvas-wrap` for the same reason: measure the box
  the anchor is verified against, not the nearest one with a matching class.
- **`closePanel` docking a survey never announced a close**, so the store went
  on believing the cascade occupied a band it had already vacated
  (`data-visible="false"` withdraws it).

### Fable's constraint, honoured and load-bearing

> **The fix must not hide a failed measurement behind a full-bleed canvas.**

It is now the first law at that site in the code. The permissive answer is
reached **only by proving both boxes are laid out** — never by inferring it
from the band's sign, which is precisely how a failed measurement would come
to wear a full-bleed canvas's clothes. A box that has not been laid out
reports 0×0, and a band computed from one means nothing. A *measured*
`band <= 0` now returns **false**: no room is a NO, not a shrug.

That the branch turned out not to be E1's cause does not retire the
constraint — it was wrong before and it is right now, and the ruling stands
on its own merits.

## §5 · E2 — HELD, AND WHY IT IS NOT A BUG

**E2 does not reproduce as an anchor that slips.** Measured on a board:

| condition | panel → stage edge | panel → board edge |
|---|---|---|
| at rest | **0.0px** | 250px |
| board canvas shrunk to 588px | **0.0px** | 250px |
| board canvas grown to 1488px | **0.0px** | 250px |
| viewport 1366→1800, 1800→1366, 1366→1680, 1680→2200 | **0.0px** | — |
| board grown, then wrap scrolled 400px | **0.0px** | — |

An early reading of 6px was a **transition artifact** — measured 600ms after a
resize while the panel was still animating. It vanishes with a proper settle,
and is recorded here so it is not rediscovered as a phantom.

**The anchor never slips. It is nailed to the app/stage edge in every
condition — and that is exactly what FX18 S2 regime (3) rules:** *"the board
is an arrangement surface, not sacred paper, so its Tutor panel keeps its
natural open-w and may overlay the canvas (**bounded to the app edge by the
flex-end dock**)."*

What Nick is seeing is real: the panel sits a constant 250px right of the
board's own edge and **does not follow the board when the board is resized**,
because it was never anchored to the board. But that makes E2 **a request to
reverse a standing ruling, not a defect to repair** — and reversing a ruling
is not this lane's act.

**The change itself is small, CSS-only, and consistent with the anchor law**
(the panel anchor keys to the board's own box under
`.desk-frame-tutor-panel-anchor--board` rather than spanning the stage). It
does not need a JS-measured position and must not get one. **On the word it is
an hour's work**, and it can ride a single suite run.

Two things worth a reviewer's eye before that word:

- the board panel currently **overlays the canvas by design** at narrow
  widths; anchoring to the board edge changes what it overlays, and that
  interacts with regime (3)'s own overlay exception;
- `.board-canvas-wrap`'s right edge does **not** move when the canvas is
  resized (the canvas overflows and scrolls inside it), so "follows the board"
  needs to be defined against the box the writer sees — the wrap — and it will
  still not track a canvas resize. If what Nick wants is the panel tracking
  the canvas, that is a different and larger change.
