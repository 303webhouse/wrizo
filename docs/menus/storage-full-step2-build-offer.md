## The shape, built
- **`idbStore.ts`** — one IndexedDB database, one object store per collection, one row per record (ruling item 3). `idbCommit` does puts AND deletes in ONE transaction, so a flush that both edits and hard-deletes in the same tick commits or fails together.
- **`writeAheadJournal.ts`** — the synchronous localStorage write-ahead journal (ruling item 1). Holds only records not yet confirmed committed; tombstone entries (`{ deleted: true }`) for the app's one hard delete (`clearDraft()`); its own failures report through storageHealth.ts under the name `writeAheadJournal`, the same channel step 1 built.
- **`storageMigration.ts`** — once, verified by read-back and count, never by "did the promise resolve" alone (ruling item 4). Signed-in clears legacy localStorage the same boot; signed-out waits for a SECOND independently-verified boot before touching the only other copy.
- **`persistence.ts`** — `cache` starts at the same empty shape a fresh device already has; `hydrate`/`flush` fork on `indexedDbAvailable()`, with the legacy whole-blob path kept byte-identical for a device with none. `flushNow()` keeps its exact synchronous signature and contract: by the time it returns, every pending record is in the write-ahead journal, even though the real IndexedDB commit is still in flight. `storageReady` is a new export; `App.tsx` awaits it alongside its existing `apiMe()` call (parallel, not serial — a local disk read is expected to resolve before a network round trip does).
- **`storageHealth.ts`** gained `reportStorageUsageFraction()` — the precise form, fed by `navigator.storage.estimate()` once IndexedDB makes a real quota available, replacing the assumed-5MiB-floor heuristic for this path (named honestly in step 1's own S0 as what step 2 would do).

## A real bug, found by the harness, not assumed away
The race guard — telling a commit's completion "am I still the latest edit for this id, or did a newer one supersede me while I was in flight" — first used each record's own `updatedAt` (a millisecond-resolution timestamp) as the discriminator. **This harness's own fuller run produced two edits to the same id landing in the SAME millisecond**, making the comparison a false match: a stale completion wrongly cleared a newer edit's journal entry, which a crash immediately after would have made permanent and silent. Fixed with a single globally-incrementing integer, stamped the moment each flush queues a commit — immune to clock resolution by construction. Caught because the falsification test for this exact guard went green when it should have gone red, and the investigation (comparing an isolated run against the full sequence) found the collision rather than assuming the guard was simply fine.

## Falsification (5 mutants, source-level, each confirmed landed and each red)
The race guard removed (a crash loses the newer edit) · the synchronous journal write removed from `flush()` (breaks the 35-call-site contract) · the tombstone bookkeeping removed (a hard delete never reaches IndexedDB) · the signed-in/out asymmetry collapsed (a signed-out writer's only copy cleared after one pass) · migration verification weakened to "did it throw" (a silently-failed write declared migrated).

## What the harness proves directly (not described, run)
`flushNow()`'s synchronous contract, read at the instant of return (the journal has it; IndexedDB does not yet) · one row per record (editing `projects` never re-touches `journalEntries`' own store) · the race guard, via releasing ONE queued commit while a second stays frozen and checking what survives a simulated crash before the second ever lands · boot replay recovering a record whose commit never happened, then re-queuing it through the normal flush cycle (not a special replay-only write path) · the legacy fallback, untouched, when IndexedDB is absent.

## A new fake, built rather than a new dependency
No native IndexedDB in Node, and no polyfill pulled in (the ticket's own "no new deps unless needed" — a ~150-line surface didn't need one). `fakeIndexedDB.mjs` models REAL transaction atomicity (staged writes, applied to the backing map only on commit) specifically so a "crash" can be simulated as "never release this transaction" and a fresh module instance's own read correctly sees nothing from it — the same property a real crash has.

## Owed — the one thing this build cannot prove itself
Ruling item 5's CDP experiment (S0 §3, refined by this build): a real browser tab, a real IndexedDB write, closed at several offsets, reopened against the same database, reading back a survival RATE — and confirming the journal recovers every case IndexedDB itself misses. Needs a box turn; the harness design is written, nothing more can be done without one.

## Unmeasured, named
`navigator.storage.estimate()`'s availability varies by browser/context (not all expose it); where it is absent, the IndexedDB path simply never shows a near-full warning — informational, not the failure channel, so this is named rather than treated as a gap to close now. The CDP experiment's real-world numbers remain the open question step 2 was built to eventually answer.
