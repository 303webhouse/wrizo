# STORAGE-FULL — STEP 1: A FAILED SAVE IS NEVER SILENT (tools lane; branch `item-storage-full`, from origin/main @ 4cb182f)
### Urgent (Nick, 2026-09-30, on being told this was urgent: "Yes."). Browserless, offered by itself, per Fable's instruction. `item-storage-full.mjs` 34/34 (park count 0). `tsc` 0, `build:web` 0, the three standing guards pass.

## The defect, verified at the bytes
`persistence.ts`'s `flush()` has always caught a `localStorage.setItem` failure with its own comment: *"Storage full/unavailable — never throw into a write path."* True, and correct — but nothing downstream was ever told, so at ~5 MB (the Publish pass's own measured figure, `docs/publish/pub-committee-pass.md` §11) saving stops with no signal, and an edit that only ever lived in memory is lost on reload.

## The three things this step does (all in `storageHealth.ts`, a new pure pub/sub module — the seam between `persistence.ts` and `sync.ts`, neither of which imports the other because of it)
1. **A per-collection FAILED flag.** `flush()`'s catch now calls `reportFlushFailed(name)`; its try branch calls `reportFlushOk(name)`. Idempotent while a collection stays failed (repeated failed writes from continuous typing don't flood the listener set), and cleared the moment that SAME collection's next write succeeds.
2. **Push at once.** The empty→non-empty transition of the failed set fires an edge event exactly once; `sync.ts` subscribes to it and calls `syncOnce()` — closing the loss window between now and the next 20s tick (or a reload/crash before it) for an edit the cache still holds but the disk copy of it does not. `syncOnce()`'s own `inFlight` guard makes this harmless if a push is already under way, and if the device is actually offline it fails exactly as any sync tick already does.
3. **A one-time near-full warning at 80%** of an assumed 5 MB floor (the Publish figure — a conservative floor, not a claimed quota; real browsers vary). Persisted ("once ever," not once per session) with hysteresis: dropping back below 70% re-arms it, so freeing real space lets a later climb warn again. `persistence.ts` computes the total from each collection's own just-stringified length (no re-reading localStorage), throttled to once per 4s so continuous typing never turns the check into its own cost.

## The words (lexicon; no meter, no count — reusing item 203's existing corner notice)
`syncNoticeText`'s priority is now: **storage failed** (most urgent — an active local write is failing right now) → offline → too-large → **storage near-full** → nothing. Two new keys: `syncStorageFull` ("This device is out of storage — the latest changes are not saved here") and `syncStorageNearFull` ("This device is running low on storage"). `ChromeControls.tsx`'s `SyncIndicator` wires both new subscriptions in.

## Falsification (5 mutants on the real source text, bundled and run in Node against a fake localStorage/window — not a description of the wiring, the wiring itself)
Idempotency removed (would re-notify on every failed keystroke) · hysteresis removed (would clear the warning on a small dip instead of a real recovery) · `syncNotice.ts`'s storage-failed priority removed (offline would win instead) · `reportFlushFailed` call removed from `flush()`'s catch (a real failure would go silent again) · the `sync.ts` bridge subscription removed (a failure would push nothing). All five land and all five go red.

## A real instrument bug, found and fixed while building the harness
esbuild strips plain `//` comments from its bundled output (not "legal comments"), so a comment-only nonce meant to force a fresh module instance per test produced **byte-identical bundles** — the same `data:` URL — and Node's module cache silently reused the FIRST instance, which had already run its side effects against the first fake `window`. Every "second session" test was silently exercising the first session's state. Fixed by exporting a real binding (`export const __harnessNonce = N`) instead of a comment; confirmed by printing the built text was in fact byte-identical before the fix.

## Measured while proving the near-full path through the real pipe (not just the pure module)
`flushNow()` — called by every durable test seam, and also at real page-hide — flushes **all six collections in one synchronous burst**, in a fixed order, and the 4s usage-check throttle can be consumed by an earlier, small collection's own flush a moment before the large one updates its share of the running total. The total (`lastFlushedChars`) still accumulates correctly across the burst regardless of order, so nothing is lost — a subsequent flush inside the same throttle window (any further typing, or the next 20s tick) reports the true total. In ordinary typing this never matters (one collection debounces at a time); it is a real property of `flushNow()`'s bursts, named here because the harness had to wait past it rather than assume it away.

## Unmeasured, named
Real browser localStorage quotas vary (Chrome/Edge roughly 5-10MB per origin; Firefox and Safari differ). 5MB is the danger floor Publish measured, not a claim about any given browser's ceiling — a device with more headroom gets an early, harmless heads-up. `persistDirty()`'s own separate `localStorage.setItem` (the dirty-id journal) keeps its original silent catch, unchanged — out of this step's per-collection scope; it fails in practice only in lockstep with whichever collection's flush is already failing, so it inherits that collection's notice. No UI beyond the existing corner text was touched (no toast, no new element) — matches the app's standing no-nagging law.
