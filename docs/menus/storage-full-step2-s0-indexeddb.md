# STORAGE-FULL STEP 2 — S0: THE SHAPE, BEFORE BUILDING (tools lane; branch `item-storage-s2-indexeddb`, from origin/main @ 8345206)
### Report only. Nothing built, nothing committed to product code. Step 1 (`item-storage-full` @ `c648c56`) and the 148 census (`item147-148-guards`) are the map this reads from.

## 0 · THE ASK, RESTATED EXACTLY
*"Move the device store to IndexedDB. The in-memory cache stays the synchronous read path, so no reader changes (Publish reads through it too); load and flush move to IndexedDB; existing keys migrate once. The hard question is durability at page hide — localStorage was synchronous and IndexedDB isn't — so measure what survives a close inside the 300ms window."*

**The headline finding, ahead of everything else: the hard question is bigger than the 300ms debounce window.** `flushNow()` — the function this app already calls at the moment it believes a write MUST land — is invoked **synchronously, and relied on as synchronous, in 35+ call sites across product code**, not only in test seams. Moving it onto IndexedDB does not just add a migration step; it inverts a contract the whole app, not just the harness suite, currently depends on.

## 1 · WHAT STAYS, WHAT MOVES (the shape)
- **`cache: Cache`** — the in-memory object every one of persistence.ts's ~130 exported getters reads from (`getJournalPages()`, `getProject()`, …) — **is untouched.** Every reader keeps its exact synchronous signature and body. This is the promise "no reader changes" and it holds: Publish, the sync engine, every component — none of them read storage directly; they all go through `cache`, and `cache` is still a plain in-memory object read with `.filter()`/`.find()`, never an `await`.
- **`hydrate<T>(key)`** (module init, today: `localStorage.getItem` + `JSON.parse`, **synchronous**) → becomes **async**, reading an IndexedDB object store per collection. This is the one place synchronicity is structurally impossible to keep: **`cache` cannot be populated at module-evaluation time any more.** The module now exports a `storageReady: Promise<void>` (or equivalent), and **`cache` starts as the SAME empty-array shape it already defaults to on a fresh device** — a device with nothing stored today already boots with `cache.journalEntries = []` etc., so a brief "render once more, now with data" is not a new SHAPE of state, only a new TIMING of when it is first populated. **App.tsx's existing boot gate (`authState: 'loading'`) is the natural place to also await `storageReady`** — the UI already shows a boot screen before anything reads `cache` in anger; this is additive to that gate, not a new one.
- **`flush(name)` / `persistDirty()`** (today: synchronous `localStorage.setItem`) → become **async** (an IndexedDB `readwrite` transaction, resolved on `transaction.oncomplete`). **`flushNow()` (today: `Object.keys(KEYS).forEach(name => flush(name))`, fire every collection, return) becomes `async function flushNow(): Promise<void>`, returning once every collection's transaction has committed (or failed).**
- **The dirty journal, `storageHealth.ts`'s per-collection report, and the near-full/quota logic are UNCHANGED in shape** — they react to "did this write succeed," not to *how* it is written. `storageHealth.ts`'s `reportFlushFailed`/`reportFlushOk` calls move from `flush()`'s `try`/`catch` to its new `.then()`/`.catch()`, nothing else about them changes.

## 2 · THE REAL RIPPLE: `flushNow()` IS A PRODUCT CONTRACT, NOT ONLY A TEST ONE
Measured on current `main` (`grep -rn "flushNow()" src`): **35 call sites outside `persistence.ts`/`sync.ts`/`storageHealth.ts`.** Two shapes, both load-bearing:
1. **`flushNow(); navigate(...)`** (`BoardEditor.tsx`, `CascadePanels.tsx`, `ScriptEditor.tsx`, `PageEditor.tsx`, `PlacesPanel.tsx`, `QuickSprint.tsx`, `BeatWizard.tsx`) — "the edit lands before the surface that holds it unmounts." **Lower real risk under async**, because an in-SPA route change keeps the JS module (and the in-flight transaction) alive; the write can finish in the background after `navigate()` returns, as long as the WHOLE APP doesn't unload.
2. **`visibilitychange → 'hidden'` → `flush(); flushNow();`** (`PageEditor.tsx`, `JournalEntry.tsx`, `ScriptEditor.tsx`, `Spread.tsx`) — **this is the app's REAL production durability net today**, and it is exactly the mechanism Fable's question is about. It fires not only right before a close, but on every tab-switch and backgrounding — most of the time the page stays alive for seconds or longer afterward, so an async write issued here has ample time to land. **The genuine new risk window is narrow and specific: the user backgrounds the tab (triggering the async flush) and then closes the browser/tab within the small number of milliseconds before that transaction's `oncomplete` fires** — a window that did not exist when `flush()` was synchronous, because by the time the old `flushNow()` returned, the byte were already on disk.
3. **`durableSeam()`'s own contract** (6 direct callers in `persistence.ts`, plus `durable()` wrapping 8 more — the namespace-member seams item 148 found) — today: `(...args) => { const out = fn(...args); flushNow(); return out; }`, **synchronous return.** This is what the whole "seed through a seam, never raw localStorage" harness law is built on: a fixture calls `window.wrizoCreateJournalPage(...)` and trusts the row is ON DISK by the time the call returns, before the very next line reloads the page. **Async `flushNow()` breaks that trust completely** — `durableSeam` must become `async`, every `window.wrizoX` test seam's TYPE changes from "returns a value" to "returns a Promise of a value," and **every harness call site that currently does `app.evalJs("window.wrizoCreateJournalPage(...)")` and reloads on the next line must instead `await` it first.** The 148 census is the map of exactly which seams these are; this is the map's second use, beyond durability auditing — it is now also the migration's own checklist.

## 3 · DURABILITY AT PAGE HIDE — RESEARCHED, NOT ASSUMED
No build-tool or spec gives a synchronous guarantee here, so this was read rather than guessed:
- **There is no spec guarantee that an in-flight IndexedDB transaction completes before a page is torn down** — confirmed across MDN discussion and the IndexedDB durability literature; this is a known, named gap in the platform, not an oversight in this plan.
- **A transaction STARTED INSIDE a `beforeunload`/`unload` handler is explicitly unreliable** (MDN: such transactions are typically aborted before they can execute) — which is exactly why this app already does NOT use those events; it uses `visibilitychange → 'hidden'`, which fires far earlier and keeps the page alive far longer in the overwhelmingly common case (tab-switch, backgrounding) — the better-behaved of the two real options, already chosen.
- **Chrome's default IndexedDB durability mode is `"relaxed"`** (a 2021+ change, [Chrome Developers](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed)): `transaction.oncomplete` can fire before the OS has actually flushed the write to disk. For THIS app's purposes — surviving a tab close, not an OS crash — relaxed durability is very likely sufficient (the renderer process doesn't die the instant a tab closes; the OS-level flush has time), but it is a NAMED assumption, not a proven one, and `"strict"` durability is available as an explicit per-transaction option at a latency cost if the measurement below says relaxed isn't enough.
- **[Sources](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed), [MDN-adjacent discussion on the unload problem](https://vaughnroyko.com/offline-storage-indexeddb-and-the-onbeforeunloadunload-problem/).**

### THE EXPERIMENT (designed now, run on the next box turn — this is what "measure" means here)
A harness cannot script "the user clicks the X button" realistically, but CDP can drive the equivalent (`Target.closeTarget` / closing the tab via CDP mid-transaction) against a REAL IndexedDB write, which is the thing worth measuring (not a simulation of it). Matrix:
| trigger offset (from the `visibilitychange: hidden` flush firing) | what it tests |
|---|---|
| 0 ms (close issued the SAME tick the async write starts) | the worst case this risk window produces |
| ~half the IDB round trip (measured first, unknown yet) | the realistic "user closed fast" case |
| after `oncomplete` has definitely fired | the control — must always survive |
For each offset: seed a page, trigger `visibilitychange: hidden` (the real event, not a simulated call), close the tab via CDP at the offset, **reopen a fresh page against the SAME IndexedDB database, and read the row back.** Repeated enough times (not once — this is exactly the kind of timing-dependent result the "measure the distribution before calling it variance" law exists for) to report a survival RATE at each offset, the same shape as m3's render-fidelity measurement, not a single pass/fail.

## 4 · MIGRATION — EXISTING KEYS, ONCE
- **What migrates:** the six collection keys (`KEYS` in `persistence.ts`) and the dirty journal (`DIRTY_KEY`). **What does NOT migrate:** `page_defaults`, theme prefs, device fonts (`wrizo-device-fonts`), the near-full-warned flag, `LAST_SYNC_KEY` and every other small, independently-owned `localStorage` key — none of them are `persistence.ts`'s collections, all are comfortably small (KB, not MB), and moving them would be scope the ticket never asked for.
- **Shape:** on first boot after this ships, before serving any read, check for a migration-done flag (its own tiny `localStorage` key — small, synchronous, cheap, and itself immune to the quota problem by construction). If unset: read each of the six+one keys from `localStorage` **exactly as `hydrate()` does today**, write them into their IndexedDB object stores, verify each write (re-read, compare), **then and only then** set the done-flag and leave the `localStorage` keys in place (never delete on the first ship — a device that rolls back to an older build must not come up empty). A later, separate item can delete the stale `localStorage` copies once this has been live and unremarkable for a while.
- **A device with no IndexedDB at all** (very old browsers; some locked-down/private contexts): **falls back to the EXISTING localStorage path, unchanged** — this ships no regression for a device this rare, and it means the storage-adapter boundary is a single seam with two implementations behind it, not a hard cutover.

## 5 · LEAN, AND THE RIVAL
**Lean: build it as designed, keep `visibilitychange: hidden` as the flush trigger (unchanged), accept and NAME the new narrow risk window from §3 rather than pretend the old synchronous guarantee still holds post-migration.** The 300ms debounce stays 300ms — IndexedDB has no cost argument for shortening or lengthening it; the real variable is the TRANSACTION's own completion latency, not the debounce.
**The rival, in its strongest form — keep a TINY synchronous localStorage shadow:** on every `flush()`, also write a small, cheap marker (not the data — just "collection X has a pending write, stamped at time T") to localStorage, synchronously, in addition to the async IndexedDB write. On the NEXT boot, if a marker exists whose IndexedDB write never completed, the app at least KNOWS a write was lost (storageHealth.ts's own "a failed save is never silent" philosophy, applied to this new failure class) — it cannot recover the bytes, but it can tell the writer honestly rather than silently serving stale data. **Its cost:** a second storage mechanism to keep in sync, for a narrow window that the box-turn measurement in §3 may show is vanishingly rare in practice. **The unmeasured risk sits on the lean:** nobody has yet measured how often the window in §3 is actually hit on a real device, so "accept it, name it" is a confident-sounding choice resting on literature, not yet on this app's own numbers.
