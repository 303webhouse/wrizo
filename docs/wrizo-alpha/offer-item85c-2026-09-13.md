## §2 · THE MIGRATION'S LAW (ratified; every file obeys it)

1. **`origin` and `source` are carried EXPLICITLY** — `null` where the row
   genuinely has no such field, the row's own value where it has one. The seam
   defaults `origin` to `'journal'` and hardcodes `source: 'page'`, so silence is
   a REWRITE, not a migration: absent `source` is what makes a row a raw capture
   (`computeFragmentItems` filters `e.source !== 'page'`), and absent `origin` is
   the pre-AB3 grandfather shape.
2. **`source: 'page'` is dropped** — the seam sets exactly that.
3. **`updatedAt` is dropped when textually equal to `createdAt`** — likewise.

Nothing else about any row changes. A field is carried as it is; **null is the
fact of absence, never a default.**

**IDS ARE RETURNED, NEVER SUPPLIED.** `createProject`/`createStoryPlan`/
`createDrawer` generate their own ids; overriding that would mean changing the
store's creators rather than the door. Fixtures adopt the returned id — locally
where it never leaves its block, and threaded through where it does (`fx9`'s
`seedFixture` and `j6`'s `seedFromDesk` now return their values, because `window`
state does not survive the reload in between).

## §7 · WHAT THE WAVE-2 PAIRS FOUND (three reds, three real defects, all mine)

### The root: a seeded `updatedAt` never reached storage

`upsert` stamps `updatedAt = new Date().toISOString()` unconditionally, on the
clone it inserts. A fixture seeding `updatedAt: t(100)` therefore never got
`t(100)` into storage — every seeded row landed in one millisecond — and the
assertions reading a recency order ("last-opened anchors first") had nothing left
to order by. Measured, not inferred: asked `2020-05-05`, returned `2020-05-05`,
**stored `2026-09-15`**.

**RULED AND BUILT (2026-09-15, parts 1 and 4).**

1. **The order is made real rather than fabricated.** `wrizoTouchInOrder` touches
   the rows in the intended sequence and lets the store stamp them ascending.
   Verified FIRST, as ruled, that no dependent assertion tests a DURATION: a
   sweep of `fx9` and `b2` for `Date.parse`, `getTime()`, `- new Date` and
   `updatedAt`/`createdAt` inequalities returns **nothing** — every dependent
   assertion tests order, count or distinctness. **Nothing was parked on duration
   grounds, because nothing needed to be.**

2. **The seam returns what was STORED.** Every creating seam re-reads through the
   store's own getters before returning. **No product-path change was required.**
   `wrizoPatchEntry` needed none — `patchJournalEntry` already ends
   `return getJournalEntry(id)`.

   > **A SEAM RETURNS WHAT WAS STORED, NOT WHAT WAS ASKED — A WRITE PATH THAT
   > ECHOES ITS INPUT CAN CERTIFY A WRITE THAT DID NOT HAPPEN.**

   Reverting to raw writes was refused; making `upsert` honour a supplied
   `updatedAt` was refused as house work. Neither was done.

### Then the minifier, which the first fix uncovered

`fx9` went green; `b2` stayed red at 3/84, S7 anchoring **Alpha Board** instead of
the loose doc, the Alpha cluster missing from the headers. The fixture looked
wrong. It was not. `wrizoTouchInOrder`'s first shape separated the stamps by
waiting for the clock:

```js
const tick = Date.now();
while (Date.now() === tick) { /* to the next millisecond */ }
```

**That loop is not in the built bundle.** Its body is empty and esbuild treats
`Date.now()` as side-effect-free, so the statement is dead code and was removed.
The source read as though the rows were a millisecond apart; the bundle stamped
all five identically. One cause, three red lines, every one pointing at the
fixture.

Two measurements settled it rather than an argument: **main's own `b2` passed
84/84 on the same bundle**, so the tree was not at fault; and a rebuild after the
first edit produced a **byte-identical asset**, proving the build was reading the
edited file all along and the loop was being deleted.

**The fix does not wait for time; it reads back state.** The loop exits on the
STORED stamp — it keeps writing until storage shows the row strictly later than
the one before it, bounded at 5000 attempts so a store that refuses to advance
fails as a visible bad order rather than a hung page. A condition that depends on
stored state cannot be elided. Verified **in the bundle**, and measured live:
five rows, five ascending stamps.

> **A LOOP THE OPTIMISER CAN PROVE EMPTY IS NOT A FACT. VERIFY BEHAVIOUR IN THE
> ARTIFACT THAT RUNS, NOT THE SOURCE THAT DESCRIBES IT** — and never express a
> requirement as elapsed time when it can be expressed as state read back.

### Then the check the fix was supposed to break

Pair 2 came back NOT CLEAN at 84/85. The one red was **`item85c.mjs`'s own**
check, asserting seven seed fields reach the row *"including a
createdAt/updatedAt that DIFFER"*. That was never true of **storage** — only of
the object the seam returned, and the seam was returning its own input. The
moment the seam reported storage, nothing held the check up. *A check can pass
for the wrong reason when its premise is already dead* — this repo's canon,
arriving on the file that earned it.

Bending `upsert` was already refused, so **the key went instead**:

- **`JournalPageSeed` loses `updatedAt`**, and `createJournalPage` loses the
  assignment that never survived the following line. The function's own doc
  comment already read *"`updatedAt` is NOT seedable and is deliberately not
  faked"* — **the code now agrees with its own documentation, which is the whole
  of the repair.** An accepted key that is silently discarded is the same lie at
  the door: it lets a fixture believe it wrote something it did not.
- **Cost of removal, counted after rather than before.** BEFORE: **6 of 192**
  `wrizoCreateJournalPage` call sites passed `updatedAt` — five in `b2`'s S7
  (already superseded by the touch) and one in the check itself. AFTER: **2 of
  194**, both in `item85c.mjs`, and both supply it **deliberately**, to prove the
  value is REFUSED. No fixture anywhere still passes the key believing it works.
  `createJournalPage` has zero call sites in `apps/desktop/src`, so this is door
  work with no product blast radius.
- **The check is PARKED verbatim** — `item85c.mjs` becomes its own first tenant
  of the A4 scaffold — and the live successor **inverts the default and proves
  the exception**: a supplied `updatedAt` is REFUSED, storage holds the write's
  own stamp, and the seam reports that stamp. The removal is checkable rather
  than claimed.
- **`b2`'s five S7 rows drop the dead `t(1)..t(100)` spacing**, which never
  reached storage and read as though it established the very order the section
  asserts.
- **S1's attached-seam roster went from 8 names to all 11.** Never falsified — it
  simply could not fail for a seam it did not know about, which is the quieter

## §9 · THE TWO RESIDUALS, RULED INTO THIS WAVE AND BUILT

### (1) The three silent setters

`wrizoSetCurrentBeat`, `wrizoSetBeatStatus` and `wrizoSetProjectDrawer` wrapped
store functions typed `void` that bail silently on a missing row, so they
returned `undefined` whether the write landed or never happened — the echo lie's
twin, failing by **silence**. Ruled: *a seam reports what happened, and "nothing
happened" is a thing that happened.*

The verdict is computed **in the seam**, by re-reading the row and checking the
change actually took: the stamped record on success, `false` when nothing
happened. **No store function's signature is touched** — that would be a
product-path change and it stops.

`setBeatStatus` has **two** silent bails, not one (missing plan, missing beat
note), so its read-back checks the **note's status** rather than the plan's
existence — otherwise a valid plan with a wrong `beatId` would report success.
Found by asking what each silent path meant, not by counting them.

One check per seam that a missing row returns `false`, and the checks
**discriminate**: a seam still returning `undefined` reads as `'undefined'`, not
`false`, so they cannot pass on the old behaviour.

### (2) S1's latent flake

The control required `updatedAt === createdAt` on an unseeded row. Those are two
clock reads — `createdAt` at function entry, `updatedAt` by `upsert` microseconds
later — and while the seam echoed its input the check compared a single value to
itself. Once the seam reported storage they agree only within a millisecond.
Parked verbatim with its reason; the successor asserts the order.

> **A CHECK THAT DEPENDS ON TWO CLOCK READS AGREEING ASSERTS AN ORDER, NEVER AN
> EQUALITY.**

### And the guard caught me — then proved too blunt to be right

Rewriting the three seams turned the durability check red: it read a fixed
`lines.slice(i, i + 4)` window and called two of them undurable while they call
`durable()` on their return. Checking the matcher rather than obeying it found
the same window had a **second fault in the opposite direction** — it reaches
PAST the seam it judges into the next one, so an undurable seam beside a durable
neighbour would have **passed**: a false negative in the one check whose whole
job is catching the seam somebody forgot.

> **A GUARD THAT FIRES IS CHECKED, NOT OBEYED — IT CAN BE WRONG IN BOTH
> DIRECTIONS AT ONCE.**

Replaced with the seam's own **brace-matched body**, bounded at the semicolon
closing the assignment at depth zero, strings and comments skipped — the
discipline the call-site parse check in the same file already used. Seam count
unchanged at **13**, so the rewrite did not quietly stop counting anything.

Both faults are now **falsifiable rather than described**, on synthetic text
(proving them against the real file would mean contriving the file into the shape
that fails). The check's own detail carries the measurement:
`oldWindowSawDurable: true`, `newMatcherSeesDurable: false`. The first version of
that falsification **failed on its own construction** — its synthetic neighbour
fell outside four lines, so it did not demonstrate what it claimed — and was
corrected, not loosened.

> **A FALSIFICATION THAT FAILS ON ITS OWN CONSTRUCTION IS CORRECTED, NEVER
> LOOSENED.**

Mutation-tested on committed work: stripping `durable()` from a long-bodied seam
is still caught.
