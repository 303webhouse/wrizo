## §2 · WHY THE SUBSET IS NOT THE PREDICTED ONE

The brief named **(b) resize-once, (e) unlink and (c) edge-vanish** as
"smallest", and card B/I/U as the one that might not fit. S0 inverted that.

**S0 pass 1 drove (b) and (c) headlessly against the shipped bundle and NEITHER
REPRODUCED.** Mouse pointer, 1400×900, DPR 1, one text card on a fresh user
board:

- **(b)** Resize #1 grew the card 435×87 → 525×157. Resize #2, immediately
  after, with **no intervening click on another card**, grew it again
  525×157 → 615×227. The handle re-armed and tracked to the new corner.
- **(c)** A card dragged far past the top-left edge **clamped** to (146,168)
  against a canvas origin of (146,167) and stayed rendered.
- **(e)** could not be set up at all: a move-drag on a second card did not move
  it, and the thread gesture minted **zero** connections. It is UNTESTED, not
  absent.

**This is as much a statement about the instrument as the product, and it is
not a claim that Nick was wrong.** He reported these from his own hands. Four
variables differ between his conditions and the probe's, and any of them could
carry the defects: **pointer type** (the probe drove a mouse), **card kind**
(text vs `page-pin`, a different `canResize` path), **card count** (defect (d)
says board resizing decays *"as cards accumulate"* — state one card cannot
produce), and **viewport/DPR**. The probe's own move-drag failing is direct
evidence the harness does not yet drive this surface faithfully.

**What is owed before any of those three is built: a reproduction under Nick's
own conditions, with at minimum pointer type and card kind named.** A fix built
against a defect that does not reproduce is a fix aimed at nothing, and a
harness that "passes" against one is worse than no harness — so `item118.mjs`
deliberately asserts **nothing** about (b), (c) or (e).

**One thing the probe settled, worth keeping.** Board `boxes` live in
BoardEditor's local React state and reach `localStorage` only on the 2s
autosave or unmount. The first probe drafted read `localStorage` and got `[]` —
it would have "confirmed" resize-once by comparing two empty arrays.
Re-instrumented to the DOM, the same run showed both resizes working. **Any
future item-118 harness must measure the rendered card, never the stored row.**

## §3 · DEFECT (a) IS THREE FAULTS, AND THE CHARTER'S GUESS IS WRONG

The charter says B/I/U is *"likely its own renderer path"*. It is not — the
card popup shares the page's engine **correctly** (`applyFormat` +
`decorateEditorFor`). Read in source, (a) splits three ways:

**(a-i) UNDERLINE HAS NO RENDERER, ANYWHERE — AND IS OFFERED ON TWO SURFACES.**
The card dock ships a `U` button (`BoardEditor.tsx:572`) and so does the page
rail (`Sliver.tsx:361`/`:398` → `PageEditor.tsx:645`). Both write `__word__`
(`draftFormat.ts:33`). Nothing renders it: `draftDecoration.ts` contains the
string "underline" **zero times**; `index.css` has `.md-bold`/`.md-italic`
(`:4200-4201`) and **no `.md-underline`**. So underline is literal and unstyled
on the page as well as the card. The shipped UI and the shipped renderer
disagree — and the decorator's own header says *"Bold/Italic ONLY"* directly
above a dock shipping three buttons.

**→ ROUTED TO FABLE, NOT TAKEN.** Two lawful repairs point opposite ways:
retire the U buttons (honour the frozen Bold/Italic set the decorator was
written to) or give underline a renderer (honour the UI that has been shipping
to the writer). Nick naming U as broken leans toward the second, but the frozen
markdown set is a **standing design ruling** and a fix lane does not unfreeze
one on its own initiative. Whichever way it goes it is one change in the
SHARED engine, landing on page and card together.

**(a-ii) THE RESTING CARD NEVER CALLED THE ENGINE AT ALL — BUILT, §4.**

**(a-iii) B/I/U ON AN EMPTY SELECTION PRODUCE BARE MARKERS, BY DESIGN.**
`wrapSelection` (`draftFormat.ts:56-59`) emits `****` and parks the caret
between the pairs; the card register is reveal-adjacent-to-caret, so both marks
render **visibly** with nothing between them. That is Nick's `****`. It is
working as specified — **and the specification is what reads as broken**: the
writer clicks B meaning "type bold from here" and receives four asterisks. A
design report wearing a bug's clothes; it wants a ruling, not a patch.

## §4 · (a-ii) — WHAT WAS BUILT

`BoardTextBox` returned `{initialText}` as a bare text node
(`BoardEditor.tsx:252-260`), so decoration ran **only** inside the opened
popup. On the board itself every marker was literal and nothing was styled,
bold and italic alike. That is the *"NO styling applied"* half of the
walkthrough report.

**The repair is not a new renderer** — it is the popup's own engine,
`decorateMarkdownForCard`, already imported in this file, called with a **NULL
caret**. The card register is reveal-adjacent-to-caret; a resting card has no
caret, so nothing is adjacent to anything and every marker collapses to
`.md-mark-hidden`. The writer gets words, not syntax.

The governing verdict already existed — FX5 S6's own: *"asterisks visible on a
card is a bug, not a style choice — the popup shows words, not syntax."* It was
written for the popup, and applies with more force to the card sitting in plain
view. **No ruling was needed and none was taken.**

**Safety.** `dangerouslySetInnerHTML` is safe here for exactly the reason it is
safe in `decorateEditorFor`, which writes this identical HTML into a live
contenteditable: every text slice passes through `escHtml`
(`draftDecoration.ts:13`), and the only tags the engine can emit are its own
`<span class="md-*">`.

**Storage is untouched, and that is asserted, not assumed.** Marks collapse via
`font-size:0` — never `display`/`visibility` — so they stay real rendered
characters and the element's `textContent` still carries the stored text
byte-for-byte. `draftDecoration.ts`'s header records why this matters: an
always-hidden marker vanishes from `innerText`, which is precisely how markdown
characters would get silently stripped out of a writer's saved words. The
harness check exists so that if anyone ever "simplifies" the hiding to
`display:none`, the failure lands loudly there rather than quietly in the
writer's words.

**Card heights.** S0 flagged that collapsed marks measure shorter than literal
ones. The measure effect is one-directional (it returns the box unchanged
unless `measured > stored`), so nothing can shrink — but reasoned is not
proven, so the height is read back and asserted.

**Deliberately out of scope, and named rather than silently skipped:**
`BoardPinBox` and the ported-card branch render a **title + excerpt**
(`notecardExcerpt`) — a derived summary of a page, not the card's own words.
Whether a summary carries styling is a design question, not a fix-lane call.
Recorded as owed follow-up.
