## §2 · THE DEFECT

`item97.mjs`'s S0 was the **first statement inside `withHarness`**, and it read
`window.wrizoPairing` with **no navigation and no wait in front of it**.

`withHarness` launches the browser **at** the app url and then connects over CDP
as fast as it can. **It never waits for the app to finish loading** — and it does
not need to, because every other harness in the roster supplies that wait itself
through its own `goto`/`waitFor`. This one file did not. The seam it reads is
installed as a **module side effect** in `store/persistence.ts`.

So the read raced module evaluation. **It won on an idle box and lost under
contention**, which is why it survived two earlier 84/84 pairs and failed on the
third.

**This is the codebase's own standing law in a form it had not taken here
before.** "A probe reads the settled state" was written for a debounce
(item 122's flush) and extended to a transition (bg2's colour). This is neither:
it is **module evaluation**, and the same sentence covers it.

**S1 through S2(e) — every one of which calls `window.wrizoPairing.birth()` —
passed in the same run.** That combination is the whole diagnosis: the seam was
installed and working; only S0's *read* of it failed. **S0 had measured the
render queue, not the product.**

Then the attribution, in the order the evidence actually settled it:

1. The seam is in `persistence.ts`, untouched by that diff — *inference*.
2. The diff was one JSX line and a harness file — *inference*.
3. The other six checks used the seam successfully — *strong, still inference*.
4. **The red run and the clean control stamped the same bundle,
   `index-DWcBCr44.js/576566b` — same name, same byte count.** The code under
   test was **the same bytes**. Not inference: the difference could not be a
   product difference, because there was no product difference.
5. A full unparked leg on clean main returned **84/84 CLEAN with `item97` green

**WHAT WAS DELIBERATELY NOT USED AS CLEARANCE:** `item97` also passes in
isolation (3/3). Recorded, and refused as an argument — isolation tests a

## §5 · THE WAIT IS WRAPPED, AND THAT IS NOT A DETAIL

`waitFor` **throws** on timeout. A driver that throws **kills the file and
reports nothing at all** — so a naive `await app.waitFor(seam)` would have traded
a flaky check for a silent one, and the regression this check exists to catch
(the seam genuinely going missing) would arrive as a dead harness rather than a
failed assertion.

So the wait resolves to a boolean and the assertion still runs:

```js
const seamReady = await app.waitFor(SEAM, { label: '…' })
  .then(() => true).catch(() => false);
```

**An absent seam must still fail as a CHECK, never kill the file** — the standing
law for every driver in this roster.
